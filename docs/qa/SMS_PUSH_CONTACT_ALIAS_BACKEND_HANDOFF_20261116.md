# SMS push contact alias — backend handoff

The iOS conversation list already displays an owner-specific saved-contact name from `ConversationDTO.displayName` / `SMSThreadDTO.displayName`. In the backend release source, `server/services/smsService.js` calls `getContactDisplayNameForPhone(uid, peerPhone)`, which uses `loadSmsContactNames` and `smsPhoneKeys` in `server/services/smsContactNames.js`. That lookup limits contacts to the receiving owner, prefers their saved alias, and matches account phones only when verified or currently assigned.

`server/routes/smsWebhooks.js` currently constructs the inbound SMS/MMS push with `alert.title: fromNumber` after `recordInboundSms` succeeds. In a separate backend change, look up `fromNumber` with `loadSmsContactNames(prisma, rec.userId, [fromNumber])`, select the first matching `smsPhoneKeys(fromNumber)` label, and use that label as the title. If there is no usable label or the optional lookup fails, retain `fromNumber`. Never use a sender-controlled display name, another account's contact, or an unverified account phone. Keep notification routing, persistence, body, and webhook acknowledgment behavior unchanged; a contact-lookup failure must not turn a saved inbound message into a Twilio retry.

Synthetic backend regression tests should cover saved alias precedence, unsaved number fallback, account isolation for the same number, verified/assigned account-phone matching, lookup failure fallback, and both SMS and MMS. iOS needs no push-title substitution: it should display the recipient-specific title supplied in the APNs payload. This backend change is **not** implemented or deployed by the iOS branch.
